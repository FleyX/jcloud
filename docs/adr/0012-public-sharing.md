# 公开分享：统一 Share 对象 + 多文件引用 + 独立公开接口

我们决定为 JCloud 增加公开分享功能：所有者可以勾选多个文件/文件夹创建一个分享（Share），系统生成一个短编码公开链接，未登录访问者通过该链接只读访问被分享的内容。

## 背景与取舍

设计初期考虑过三种分享模型：

1. **单文件分享链接**
   - 每个分享链接只指向一个文件节点（文件或文件夹）。
   - 优点：模型简单，一张表即可；与现有 `FileNode` 一一对应。
   - 缺点：用户勾选多个文件分享时，需要生成多个链接，体验割裂；无法表达“这批文件一起共享”的语义。

2. **分享包（Package）与分享链接（Link）分离，一对多**
   - `SharePackage` 保存文件集合，`ShareLink` 保存访问凭证，一个包可对应多个链接。
   - 优点：可为同一批文件创建不同策略的链接（如永久链接 + 7 天临时链接）。
   - 缺点：需要两张核心表，所有者管理页面和公开访问页都需要同时理解两个对象；与项目当前“简单直接”的风格略有偏离。

3. **统一 Share 对象，一对一（选定）**
   - 一个分享同时包含“文件节点集合”和“访问控制信息”，对应一个唯一的 `shareCode`。
   - 优点：概念单一，数据库表少（`t_share` + `t_share_item`），所有者和访问者都只需理解“一个分享”;
   - 缺点：同一批文件无法生成多个不同策略的链接；如需不同策略，用户需重新勾选创建新分享。

选择方案 3。对于个人网盘场景，一期先提供简单直观的分享体验，避免过早引入“包/链接”两层抽象。

## 关键决策

- **公开分享仅支持未登录访问者**：本期不做站内用户授权共享，所有公开访问均无需登录。
- **只读权限**：访问者可浏览列表、递归打开文件夹、预览文件、下载单个文件、下载整个分享（ZIP），不可上传、修改或删除。
- **多文件引用**：一个分享可包含多个 `FileNode` 引用，通过 `t_share_item` 表保存 `share_id` 与 `file_node_id` 的关系。
- **公开访问接口独立**：新增 `/s/{shareCode}` 系列公开接口，校验链接状态后再调用现有文件服务能力，不与登录态下载/预览接口混用。
- **短随机编码**：`shareCode` 为 8 位字母数字混合短码，排除易混淆字符，数据库唯一索引。
- **访问控制**：支持名称、描述、可选密码、有效期、最大访问次数、手动停用/启用。
- **引用失效语义**：源文件重命名/移动实时反映；源文件被删除或移入回收站后，公开视图自动过滤移除，且从回收站恢复后不会自动回到原分享。
- **分享可编辑**：创建后可增删分享项、修改访问控制、修改名称/描述、停用/启用。

## 影响

- 新增 `t_share` 与 `t_share_item` 两张表，以及对应 Flyway 迁移脚本。
- 新增 `ShareService`、`ShareController`、`ShareMapper` 等后端模块，以及公开访问相关的独立 Controller。
- 前端新增“创建分享”弹窗、“我的分享”管理页、公开访问页 `/s/{shareCode}`。
- 下载/预览服务需要支持“以文件所有者身份”读取文件，同时不依赖 `UserContext` 中的当前登录用户。

# 回收站：独立删除记录表 + 物理文件移入 trash 目录

我们决定为回收站引入一张独立的删除记录表 `t_recycle_bin`，并在软删除时将原 `t_file_node` 节点（含子树）物理删除，同时把物理文件移动到 `trash/<id 前十位>/<id>/` 下。恢复时通过遍历 trash 目录重建子树，并重新计算文件元数据。

## 背景与取舍

设计初期考虑过三种回收站方案：

1. **在原 FileNode 表增加回收站字段（软删除）**
   - 增加 `is_deleted`、`original_parent_id` 等字段，复用现有 `@TableLogic` 的 `delete_at`。
   - 优点：表结构简单，恢复时只需改状态；MyBatis-Plus 自动过滤已删除行。
   - 缺点：正常文件查询与回收站查询混用同一张表；大表长期累积已删除数据；物理文件原地保留，磁盘结构不直观。

2. **完全独立回收站记录表 + 物理删除 FileNode + 文件移入 trash（选定）**
   - `t_recycle_bin` 只记录用户主动删除的顶层节点；原 `t_file_node` 中对应节点及子节点被物理删除。
   - 物理文件按被删节点 ID 平铺到 `trash/<prefix>/<id>/`，其中 `prefix` 为节点 ID 的前十位；文件夹的子树结构保持原样。
   - 优点：正常文件表保持精简；回收站物理目录清晰，便于运维直接查看；删除与恢复是显式操作，模型边界清晰。
   - 缺点：恢复时需要遍历 trash 目录重建子树并重新计算 hash/size/mimeType；需要处理原父目录缺失、目标路径冲突等复杂场景（目标路径冲突处理统一见 ADR-0008）。

3. **内容寻址对象池 + 引用计数**
   - 文件按 hash 存放对象池，删除只减少引用计数，引用归零再清理。
   - 优点：天然支持去重、秒传；回收站只是引用标记。
   - 缺点：与当前镜像存储模型冲突；需要引入对象池与引用计数抽象；磁盘结构对人不可读。

选择方案 2。

## 关键决策

- **删除记录表只记录直接删除的节点**：如果用户勾选了文件夹 folder1 和文件 a.txt，则 `t_recycle_bin` 产生两条记录，分别对应这两个被直接删除的节点。
- **原 FileNode 表物理删除节点及子节点**：软删除后，正常文件列表查询不再看到这些节点，避免大表累积历史数据。
- **物理文件移入 trash 目录**：路径为 `存储空间路径 / 用户编码 / trash / <节点 ID 前十位> / <节点 ID> /`。文件夹的子树结构保持原样，文件按原名存放。
- **恢复时重建子树**：通过遍历 trash 目录重建所有 `FileNode` 记录，文件元数据（hash、size、mimeType）在恢复时重新计算。
- **配额继续占用**：软删除时不扣减 `user.used_space`，仅在永久删除或自动清理时根据 `t_recycle_bin.total_size` 回减配额。
- **旧 node_id 仅用于定位 trash 目录**：恢复后创建的新节点拥有新 ID，原 `node_id` 仅作为 trash 目录名和删除记录的外键引用。

## 影响

- 正常文件表不会累积已删除数据，查询性能更稳定。
- 回收站列表需要联合 `t_recycle_bin` 与 trash 目录读取。
- 恢复操作涉及物理文件移动、子树重建、配额扣减/恢复，需要在用户级写锁保护下事务执行。
- 自动清理任务扫描 `t_recycle_bin` 中超过 30 天的记录，删除对应 trash 目录并回减配额。

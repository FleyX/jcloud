# 统一文件冲突处理

我们决定将上传、恢复、移动、复制四个操作的文件冲突处理统一为同一套策略、同一套前后端数据结构与同一套冲突解决内核；文件夹冲突统一按递归合并处理；重命名与创建文件夹保持「重复即报错」的现有行为。

## 背景与取舍

当前文件管理核心功能已开发完毕，但各操作的冲突处理散落在多个 Service 与工具类中，实现不一致、前端弹窗分裂、配额计算容易出错。具体问题包括：

- **覆盖行为不一致**：上传/恢复覆盖时会物理删除旧文件并扣减配额；移动/复制覆盖时只逻辑删除旧节点，不删物理文件也不更新配额。
- **文件夹冲突处理不统一**：移动/复制的文件夹 `auto_rename` 被降级为 `skip`；恢复的文件夹 `auto_rename` 直接抛异常。
- **前端冲突 UI 分裂**：上传、恢复、移动/复制分别使用不同的弹窗/页面，默认值与键值映射不一致。
- **自动重命名语义模糊**：各调用点消费 `FileConflictHelper.generateAutoRename` 的方式不同。
- **重命名/创建文件夹无策略**：同名时直接后端报错，前端无选择空间。

统一方案考虑过两种范围：

1. **全操作统一**：把重命名、创建文件夹也纳入统一冲突策略，同名时支持跳过/覆盖/保留。
   - 优点：体验最一致。
   - 缺点：重命名/创建文件夹通常发生在单文件/单目录场景，用户期望明确失败或成功，引入策略弹窗反而增加交互负担；且重命名后如果目标名被自动改写，用户感知不直观。

2. **四操作统一 + 重命名/创建保持现状（选定）**：上传、恢复、移动、复制统一处理；重命名/创建文件夹同名直接抛异常提示。
   - 优点：覆盖了真正需要批量策略选择的场景；保留简单操作的直接反馈；改造范围可控。

选择方案 2。

## 关键决策

### 1. 纳入统一冲突处理的操作

- **纳入**：上传、恢复、移动、复制。
- **不纳入**：重命名、创建文件夹。目标位置已存在同名文件/文件夹时，后端直接抛 `BusinessException` 提示用户，前端保持现有错误提示。

### 2. 文件夹冲突统一为递归合并

- 当源节点是文件夹，且目标位置已存在同名文件夹时，**默认合并内容**，而不是当作冲突。
- 合并是**递归合并**：把源目录树中的每个子文件/子目录逐层映射到目标目录树中。
  - 目标路径上存在同名文件 → 按文件冲突策略处理。
  - 目标路径上存在同名文件夹 → 继续向下一层合并。
- 预检接口需要递归扫描源目录树，只返回真正的**文件级冲突**列表。

### 3. 文件冲突策略统一为三种

- `skip`（跳过）：保留目标位置的现有文件，源文件不写入。
- `overwrite`（覆盖）：物理删除目标位置的现有文件及节点，扣减 `used_space`，然后写入源文件。
- `keep`（保留）：自动重命名源文件为 `name(n).ext`，并存入目标目录。

后端枚举统一为 `ConflictStrategy.SKIP / OVERWRITE / KEEP`；前端展示统一为「跳过 / 覆盖 / 保留」。

### 4. 「保留」重命名规则

- 格式：`文件名(n).文件后缀`，例如 `report(3).pdf`。
- 无后缀文件：`README(n)`。
- 匹配范围：**冲突所在目录**下、与基础文件名同名的文件。
- 序号提取：按数字大小取最大值，而非字符串排序。
- 中间空缺不填补：已有 `report(1).pdf`、`report(3).pdf` 时，新文件为 `report(4).pdf`。
- 如果原始文件名本身未被占用，不会生成 `report(1).pdf`，而是直接使用原名。

### 5. 覆盖语义强制一致

- 当前未做文件内容去重（dedup）和引用计数。
- `overwrite` 统一执行以下步骤：
  1. 物理删除目标位置的现有文件。
  2. 物理删除现有文件节点（不进回收站）。
  3. 扣减用户 `used_space`。
  4. 写入源文件并更新 `used_space`。
- 所有操作（上传、恢复、移动、复制）的覆盖逻辑调用统一的副作用方法 `deleteExistingForOverwrite(existingNode)`，确保一致。

### 6. API 保持独立入口，统一数据结构

- 上传、移动、复制、恢复仍保留各自的预检/执行入口，因为参数差异大。
- 但所有预检接口返回统一的冲突列表结构：
  - `ConflictItemVo`：`nodeId`、`name`、`sourcePath`、`targetPath`、`type: file | folder`、`suggestedStrategy` 等。
  - 仅包含文件冲突；文件夹已按递归合并展开。
- 所有执行接口接收统一的操作项结构：
  - `OperationItemDto`：`nodeId`、`strategy`。
  - 可选 `globalStrategy`：当用户选择「统一全部」时，后端按此策略处理所有冲突。

### 7. 后端冲突内核分层

- 新增 `FileConflictResolver`：纯计算，不参与事务和 IO。
  - `detectConflicts(context)`：输入用户、源节点列表、目标父目录、操作类型，输出文件级冲突列表。
  - `resolveName(...)`：根据策略返回最终名称；`overwrite` 返回需要删除的旧节点标识；`keep` 调用重名算法。
  - `keepNameGenerator(...)`：按 `name(n).ext` 规则生成新名。
- 各操作 Service（`UploadService`、`FileOperationService`、`FileRecycleService`）负责具体执行，因为物理文件写入、秒传、分片合并、回收站状态等差异较大。
- 统一的副作用方法 `deleteExistingForOverwrite(...)` 由 `FileConflictResolver` 或公共工具提供，确保物理删除、配额扣减、节点删除一致。

### 8. 预检与执行的状态一致性

- 预检与执行分为两个请求，中间目录状态可能变化。
- 执行时**重新检测**每个操作项的目标路径：
  - 预检时存在的冲突在执行时消失 → 直接正常写入，忽略原策略。
  - 预检时不存在的冲突在执行时出现 → 按全局策略处理；无全局策略时默认 `keep`。
- 不引入分布式锁或版本锁，以简单和性能优先；执行结果以执行时状态为准返回给前端。

### 9. 批量操作按叶子节点独立部分成功

- 一次批量操作中的每个源文件作为独立执行单元。
- 某个文件失败不影响其他文件。
- 返回统一的 `OperationResultVo`：
  - `successCount`、`skipCount`、`failCount`。
  - `failures[]`：失败文件名 + 错误原因。
- 文件夹仅作为容器递归展开，子文件独立执行。

### 10. 边缘场景

- **移动/复制文件夹到自身子目录**：直接抛异常禁止。
- **上传时目标文件夹已被删除**：归属到「目标不存在」统一处理，返回明确错误。
- **回收站恢复时原父目录不存在**：不报错，自动创建缺失的父目录，恢复后路径与删除前保持一致。

### 11. 前端统一冲突弹窗

- 合并 `UploadConflictModal`、`ConflictResolveModal`、移动/复制内置冲突页为一个通用组件 `FileConflictModal`。
- 列表只展示文件级冲突；顶部显示摘要：`共 N 个文件冲突，M 个文件夹将自动合并`。
- 列表字段：文件名（含源路径）、目标位置、冲突类型标签、操作下拉框（跳过/覆盖/保留）。
- 单行默认策略：`keep`（保留）。
- 顶部提供「全部跳过 / 全部覆盖 / 全部保留」按钮，点击后批量设置所有行，用户仍可单独调整。
- 仅当所有行都已选择策略时，确认按钮才可点击。
- 执行完成后使用统一结果提示展示成功/跳过/失败数量。

## 影响

- 需要重构后端 `FileConflictHelper`、`UploadConflictResolver`、`FileOperationExecutor`、`FileRecycleServiceImpl` 中的冲突处理分支，统一收敛到 `FileConflictResolver`。
- `ConflictStrategy` 枚举需要从 `skip / overwrite / auto_rename` 改为 `SKIP / OVERWRITE / KEEP`，涉及前后端所有引用点。
- 移动/复制的覆盖逻辑需要改为物理删除 + 配额扣减，与上传/恢复一致，修复脏文件残留与配额计算错误。
- 前端需要合并三个冲突弹窗/页面为 `FileConflictModal`，统一策略文案、默认值、键值映射与结果反馈。
- 需要新增或修改 Flyway 迁移文件：如果 `ConflictStrategy` 以字符串形式存储在数据库中，需要迁移旧值 `auto_rename` 到 `keep`。
- 需要补充单元测试覆盖：递归合并、保留命名算法、覆盖物理删除与配额扣减、执行时重检策略兜底、批量部分成功等场景。

# 数据模型重构：定长 base36 ID、id 路径与物理删除

为了在保持有序性的同时缩短 ID 长度、简化文件树路径维护，并避免已删除数据在大表中累积，我们决定对核心数据模型进行一次重构：所有表主键及关联 ID 改为雪花算法 + 定长 base36 字符串；`t_file_node.path` 改为 id 路径；`t_file_node` 与 `t_recycle_bin` 改为物理删除。

## 背景

当前数据模型存在以下问题：

1. **ID 长度与可读性**：雪花算法生成的 `Long` 类型 ID 在 JSON、URL、日志和磁盘路径中都是 19 位十进制数字串，偏长。
2. **路径维护成本高**：`t_file_node` 同时维护 `path`（祖先 ID 快照）和 `path_name`（完整可读路径）。重命名或移动文件夹时，需要级联更新所有后代的 `path_name`。
3. **软删除数据累积**：`BaseEntity` 默认通过 `@TableLogic` 软删，虽然 `t_file_node` 和 `t_recycle_bin` 在业务代码中已经走物理删除，但表上仍保留 `delete_at` 字段，语义不一致。

## 关键决策

### 1. 所有表 ID 改为定长 base36 字符串

- 继续沿用雪花算法生成 64 位有符号 `Long`，再转换为 **小写 base36** 字符串，**左补零到 13 位**。
- 13 位足够容纳 `2^63 - 1`（`36^12 ≈ 4.7e18 < 9.22e18 < 36^13 ≈ 1.7e20`）。
- 定长后字符串的字典序与原始数字序一致，B+ 树范围查询和 `ORDER BY id` 仍保持有序。
- 所有表主键及关联字段（`user_id`、`role_id`、`permission_id`、`parent_id`、`storage_space_id`、`file_node_id` 等）统一改为 `VARCHAR(13)`。
- 通过自定义 `IdentifierGenerator` 实现，并提供 `IdUtil.nextId()` / `nextIds(n)` 公共方法供业务层使用。
- 虚拟根节点使用固定占位 id：`0000000000000`（数值 0 的 base36），所有文件树根节点的 `parent_id` 都指向它。

### 2. `t_file_node.path` 改为 id 路径，删除 `path_name`

- `path` 表示**从虚拟根到父节点的 id 路径**，不包含自身 id，使用 `.` 分割，不含前后缀 `.`。
- 字段长度 `VARCHAR(300)`；索引为 `user_id + path(70)`，业务层软限制约 5 层祖先。
- 删除 `path_name` 字段，物理路径不再由数据库字段直接推导，而是通过 id 路径查询祖先 `name` 实时拼接。
- 由于 id 定长 13 位，子树查询和批量更新可以使用 `path LIKE concat(oldPath, '%')`，不会产生名称路径时代 `/docs` 误匹配 `/docs2` 的前缀歧义。
- 重命名文件夹时不再需要级联更新子树，只有移动文件夹时才需要更新子树 `path`。

### 3. `t_file_node` 与 `t_recycle_bin` 改为物理删除

- 仅这两张表改为物理删除，其他表（用户、角色、权限、资源、存储空间等）继续软删。
- 从 `FileNode` 和 `RecycleRecord` 实体中移除 `delete_at` 字段及 `@TableLogic`。
- 回收站保留 `original_path_name` 字段，仍按删除时的名称路径恢复。

### 4. Flyway 脚本删库重建

- 由于主键类型和外键字段都需要变更，且所有 id 需要重新编码，选择**删库重建**。
- 合并所有历史 Flyway 脚本为一份新的初始化脚本，初始化数据（角色、权限、资源等）的 id 重新生成为 13 位 base36。

## 取舍

- 选择 base36 而非 base62 / ULID：base36 只含小写字母和数字，便于在 URL、日志和文件系统中使用，且不区分大小写；定长 13 位后仍比 19 位十进制短。
- 保留 `original_path_name` 而非改为 id 路径：实现更简单，恢复时按名称路径定位父目录，与现有逻辑兼容；代价是删除期间祖先重命名会导致恢复位置变化，业务上可接受。
- 物理路径仍用名称路径而非 id 路径：磁盘目录保持用户可读，便于运维和灾难恢复；代价是文件操作需要查库拼接路径，通过批量内缓存降低影响。
- 不创建虚拟根节点实体记录：只在 `parent_id` 和 `path` 中用固定占位 id 表示根，避免每个用户维护一条无意义记录。

## 影响

- 所有 PO、DTO、VO、Mapper、Controller 的 id 字段类型从 `Long` 改为 `String`。
- 前端 id 类型继续按 `string` 处理（与现有规范一致）。
- `FilePathUtil` 需要重构：入参合并为对象，支持单条/批量，批量内缓存 `id -> name` 映射。
- 子树查询、移动批量更新、回收站恢复等依赖 `path_name` 的逻辑需要重写。
- `t_recycle_bin` 的 trash 目录分层由 id 前十位决定；id 改为字符串后，目录名直接使用字符串 id 本身。
- 需要新增单元测试覆盖 ID 生成、路径解析、子树查询与批量更新、物理删除。

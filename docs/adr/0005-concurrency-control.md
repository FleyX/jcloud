# 文件写操作并发控制：异步文件夹更新 + Redisson 用户级读写锁

我们决定对文件写操作使用 Redisson 分布式读写锁，按用户隔离并发。同一用户同一时间只允许一个写操作执行，但多个读操作可以并发。涉及大规模后代更新的操作（如文件夹移动/重命名）采用异步任务执行，并在整个异步任务期间持有写锁。

## 背景与取舍

文件管理中的写操作（上传、删除、移动、重命名、恢复、清空回收站等）会同时修改数据库记录与物理文件。由于我们在 `FileNode` 中冗余存储了 `path_name`，重命名或移动文件夹会影响其下所有后代的 `path_name`，可能涉及数万行更新。

考虑过三种并发策略：

1. **同步级联更新**
   - 在请求线程里一次性 `UPDATE` 所有后代的 `path_name`。
   - 优点：实现简单，请求返回后即一致。
   - 缺点：大目录会长时间占用请求线程和数据库事务；虚拟线程下仍可能因长时间 IO 影响吞吐。

2. **异步更新但不加锁**
   - 只改文件夹自身元数据并标记 `moving`，后台异步更新后代。
   - 优点：请求响应快，用户可继续其他操作。
   - 缺点：异步更新期间可能发生并发写（如同名新建、子目录移动），导致 `path_name` 不一致或路径冲突。

3. **异步更新 + 用户级读写锁（选定）**
   - 文件夹移动/重命名触发异步任务，任务开始前获取该用户的 Redisson 写锁，整个任务期间保持持有。
   - 读操作可并发获取读锁；写操作串行获取写锁。
   - 优点：保证同一用户的所有写操作串行执行，避免路径不一致；异步任务不阻塞 HTTP 响应；分布式锁支持多实例部署。
   - 缺点：单个用户的大目录操作会阻塞该用户的其他写操作（如上传）。

选择方案 3。

## 关键决策

- **写操作串行化**：每个用户的写操作通过 Redisson 读写锁串行化。读操作可并发，写操作互斥。
- **异步任务持有写锁**：文件夹移动/重命名等需要级联更新后代的操作，在异步任务执行期间持续持有写锁，直到所有后代 `path_name` 更新完成。
- **锁复用**：Redisson 锁不仅用于普通文件操作，也复用于用户存储空间迁移、回收站清空等管理员触发的写操作。
- **状态标记**：正在执行异步级联更新的文件夹标记为 `moving` 状态，便于前端展示和崩溃后恢复。
- **崩溃恢复**：服务启动时扫描 `moving` 状态的记录，根据任务状态决定重试或回滚，避免永久悬挂。
- **两阶段冲突解决的锁保护**：上传、恢复、移动、复制等两阶段冲突解决流程中，执行阶段获取写锁，预检阶段不持锁。用户决策期间允许其他写操作，执行时按最新状态重检并按策略兜底；详见 ADR-0008。

## 影响

- 大目录移动/重命名不会阻塞 HTTP 线程，但会阻塞该用户的其他写操作直到任务完成。
- 单用户写入并发度被限制为 1，整体系统的写吞吐主要受分布式锁和物理 IO 限制。
- 需要为 Redisson 引入 Redis 依赖，并设计锁的续租与超时策略。
- 所有写操作代码路径都需要规范地获取和释放锁，防止死锁与锁泄漏。

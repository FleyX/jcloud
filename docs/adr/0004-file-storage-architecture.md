# 文件存储架构：单 FileNode + 虚拟文件树 + 镜像存储 + 每用户存储空间

我们决定采用单表 `FileNode` 统一表示文件与文件夹，使用虚拟文件树与物理存储分离的镜像存储模型。每个用户绑定到一个用户存储空间，该用户所有文件字节落在该空间内；物理路径按 `username` 在用户存储空间下隔离。系统级数据（预览图、ZIP 临时任务、配置、缓存）存放在独立的系统存储空间中，不计入用户配额。

## 背景与取舍

设计初期考虑过三种存储架构：

1. **内容寻址存储（Content-Addressed）**
   - 文件按 hash 存放到对象目录，逻辑路径与物理路径解耦。
   - 优点：天然支持全局去重、秒传、版本历史；移动/重命名只改数据库。
   - 缺点：需要对象池与引用计数抽象；磁盘结构对人不可读；与“镜像目录便于直接读取”的运维习惯冲突。

2. **文件/文件夹分表 + 物理根绑定**
   - `File` 与 `Folder` 分表，文件夹绑定物理根。
   - 优点：Schema 语义清晰。
   - 缺点：跨表一致性、路径重建、子孙级联更新都会引入复杂事务；多根目录下物理路径与逻辑路径容易错位。

3. **单 FileNode + 虚拟文件树 + 镜像存储 + 每用户存储空间（选定）**
   - 文件与文件夹同表，通过 `type` 区分；`path` 记录祖先 ID 快照，需要可读路径时通过 `path` 查询祖先 `name` 实时拼接。
   - 每个用户绑定一个用户存储空间；物理路径 = `存储空间路径 / files / username / 名称路径`，其中 `username` 为全局唯一且不可修改的用户登录名。
   - 优点：模型自洽、用户隔离明确、管理员可通过扩容/迁移管理存储、物理路径可直接从逻辑路径推导。
   - 缺点：移动文件夹需要级联更新后代 `path`；迁移用户时需要复制字节。

选择方案 3。

## 关键决策

- **统一实体**：使用 `FileNode` 表同时存储文件和文件夹，通过 `type: 'file' | 'folder'` 区分。避免分表带来的跨表一致性问题。
- **物化路径**：
  - `path` 是祖先 ID 的快照（不包含自身 ID），使用 `.` 分隔的 13 位 base36 id 表示（如 `0000000000000.parentId`），用于快速定位子树。
  - 虚拟根节点使用固定占位 id `0000000000000`；所有实际文件节点的 `parent_id` 指向真实父节点或该占位根。
  - 不再维护 `path_name` 字段；需要可读路径时，通过 `path` 查询祖先 `name` 实时拼接。
- **每用户绑定一个用户存储空间**：创建用户时指定默认存储空间，该用户所有文件字节均落在该空间内。
- **系统数据存放在独立的系统存储空间**：管理员配置一个独立的系统存储空间，用于存放预览图、ZIP 临时任务、系统配置等数据；系统数据不计入用户配额，容量由管理员监控。ZIP 任务等按用户隔离的数据存放在 `<系统存储空间路径>/zip-tasks/<username>/<taskId>` 下。
- **空间管控**：同时检查用户配额与所属存储空间容量，上传前预占配额，上传完成后转为实际已用空间。
- **用户迁移**：管理员可将用户完整迁移到另一存储空间；迁移期间用户进入只读状态，所有字节物理复制到新空间。

## 影响

- 目录浏览、权限判断、面包屑主要依赖 `FileNode` 表，物理存储布局不暴露给前端。
- 重命名文件夹只更新自身 `name`，不再需要级联更新子树；移动文件夹属于写操作，需要批量更新子树的 `path`。
- 物理路径不再由数据库字段直接推导，文件操作需要通过 id 路径查询祖先 `name` 实时拼接，批量处理时缓存已查询的 `id -> name` 映射。
- 同一用户内的去重文件可以使用硬链接，跨用户不共享物理 inode，简化了配额统计与迁移逻辑。
- 系统存储空间需要单独监控容量，避免预览图等系统数据把磁盘撑满。

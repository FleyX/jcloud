# 秒传去重：用户内去重 + 部分 hash 候选 + 完整 hash 校验

我们决定实现用户内的秒传去重。上传前先用部分 hash 快速查找候选文件，找到候选后再用完整 hash 做最终校验，确认一致则直接创建新 FileNode 并复用已有物理文件。复用优先使用硬链接，硬链接失败时退化为普通复制。去重范围限定在同一用户内，跨用户不共享物理文件。

## 背景与取舍

秒传可以减少重复上传的带宽与时间，也节省存储空间。但全局去重会引入复杂的配额归属、引用计数和迁移问题，尤其是在镜像存储模型下。

考虑过四种方案：

1. **不去重**
   - 优点：最简单，无一致性负担。
   - 缺点：用户重复上传相同文件会浪费空间和带宽。

2. **全局去重（跨用户）**
   - 不同用户共享同一物理 inode（硬链接或引用计数单副本）。
   - 优点：存储效率最高。
   - 缺点：配额归属复杂（谁为共享字节买单）；用户迁移时可能因跨文件系统无法保留硬链接；删除时需要引用计数。

3. **用户内去重（选定）**
   - 只在同一用户范围内查找重复文件。
   - 优点：配额统计简单（用户只为自己的物理字节负责）；迁移用户时无需处理跨用户共享 inode；实现简洁。
   - 缺点：不同用户间的重复文件仍会占用多份空间。

4. **全局去重但复制隔离**
   - 同存储空间内跨用户秒传使用硬链接，跨存储空间复制。
   - 优点：兼顾效率与隔离。
   - 缺点：配额与迁移问题依然存在，只是按存储空间隔离。

选择方案 3。

## 关键决策

- **去重范围**：仅在该用户的文件范围内匹配重复，不涉及跨用户共享。
- **文件身份 hash 策略**：
  - 文件小于 150MB：计算完整文件 hash。
  - 文件大于等于 150MB：取前 50MB、中间 50MB（从 `floor(size/2)` 开始）、后 50MB 拼接后计算 hash，作为候选过滤。
- **完整 hash 校验**：当部分 hash 匹配到候选文件时，服务端返回候选文件的完整 hash；客户端计算本地完整 hash 并比对，完全一致才执行秒传。避免部分 hash 碰撞导致数据污染。
- **复用方式**：
  - 同一存储空间内优先使用硬链接。
  - 硬链接失败（如文件系统不支持）则退化为普通文件复制。
  - 跨存储空间场景通过用户迁移处理，普通上传不走跨空间去重。
- **与配额的关系**：复用后的文件只计算一次物理大小，新上传不增加该用户的已用空间。

## 影响

- 大文件秒传前需要客户端计算一次完整 hash，仅在找到候选时产生额外开销，大部分上传不受影响。
- 用户内去重避免了跨用户的配额归属争议，删除文件时按普通硬链接语义处理即可。
- 管理员迁移用户时，只需复制该用户自己的文件，无需担心破坏跨用户共享关系。
- 不同用户间的重复文件会占用多份物理空间，这是为简化模型做出的取舍。
